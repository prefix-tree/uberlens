# UberLens: research on video-editing agents

The editing agents that work in late 2026 have three things in common: they look at media on demand instead of all at once, they keep evidence pinned to the exact version of the file it came from, and they watch their own output before they finish. **VIVID** (arXiv:2611.20688, MIT) is the clearest proof. It adds six tools (`catalog, inspect, transcribe, retrieve, edit, verify`) and a version-pinned evidence store to an off-the-shelf coding agent, and that lifts Codex on GPT-5.6-sol from 38.4% to 58.6% on AgenticVBench. Its ablations rank the parts by value: on-demand inspection (−16.0 pp without it), output review (−14.6) and evidence memory (−10.8). The critic papers then show how that review should be shaped. **Auto-Director**'s critic watches keyframes of the draft, scores each scene, routes one typed failure to the agent that can fix it, freezes scenes that pass and stops after 3 rounds. **EditDuet**'s critic reads only a text shot list and suggests actions the editor does not have, and that failure is the main thing to design against. **HKUDS VideoAgent** is weaker than its headline numbers suggest. Its 87–95% is plan validity judged by an LLM, its ~60% is a retrieval cost saving, and its "textual gradient" is an LLM judge-and-reflect loop capped at 3 rounds. **MMLVE-Agent** edits pixels generatively, not timelines. Index-first systems (Ding et al., CutClaw) build a description of the whole timeline before editing, but they still re-check pixels before every cut, and none of them measures whether building the index pays for itself. For UberLens, the main conclusion is that **UberScene already provides most of what these papers had to build**: a closed, validated vocabulary of 98 edit actions, a deterministic render, labelled contact sheets, a layout check that reports problems like a compiler, and a per-frame cache that knows which frames an edit changed. UberLens should therefore copy VIVID's evidence model, Auto-Director's typed and routed critic and CutClaw's code gates, and then extend version pinning from whole files down to single frames.

### VIVID: six tools and evidence pinned to a content hash

VIVID ("A Visual Harness for Agentic Video Editing", Yu, Zhang, Tan, Li and Sha) ships as a Codex or Claude Code skill, an MCP server, a CLI and a worker. It needs Python ≥3.11 and FFmpeg ([repo](https://github.com/yuwenhan07/VIVID)). It does not replace the agent's editing. The agent still cuts with its own shell, Python and FFmpeg, and the optional `edit` tool only compiles declared trims, concatenations, constant-speed changes and captions, and computes source↔output time maps ([VIVID §3.2, A.6](https://arxiv.org/html/2611.20688)). What VIVID adds is a way to see. `inspect` takes a time window, a native-pixel `roi`, `max_frames` from 1 to 24 and contact sheets of 8. In auto mode it switches to an overview of independent seeks when a span is longer than 60 s. Windows are capped at 600 s and audio at 120 s, and a request that is too long comes back bounded with a version-pinned `next_request` ([harness_protocol.py, interaction.py](https://github.com/yuwenhan07/VIVID)). **Every observation returns the timestamps of the frames actually decoded, the crop and the media version** ([VIVID Eq. 1](https://arxiv.org/html/2611.20688)).

The memory model is the part to copy. A media version is `"asset_" + sha256(relative_path + "\0" + file_sha256)[:24]`, so rewriting a file at the same path makes a new version while the old one stays recallable. An evidence ID is an opaque `ev_` + uuid4. Both are stored in SQLite (`assets`, `evidence` indexed on asset and time, `annotations`, `events`), and evidence images are kept as content-addressed blobs whose hash is re-checked on recall ([memory.py](https://github.com/yuwenhan07/VIVID)). `retrieve` is an exact evidence-ID lookup or a literal, case-insensitive all-terms text search. It has no embeddings and does not search pixels, and the tool says that "a miss does not establish absence in raw media". Task state lives in TASK.md, GUIDE.md, WORKING.md and a regenerated MEMORY.md capped at 16 KB. A `VIVID_CHECKPOINT` continues the work in a fresh context, and the budget carries over ([VIVID A.1–A.5](https://arxiv.org/html/2611.20688); [notes.py](https://github.com/yuwenhan07/VIVID)). `verify` checks hash, streams, a bounded full decode and the expected size, duration, codecs and channels. Given a timeline, it also plans review windows around cuts, and says plainly that "review windows do not establish semantic success". The prompt adds three guardrails: sampled frames are not continuous coverage, a transcript is not proof of listening, and technical checks do not establish quality ([VIVID A.4](https://arxiv.org/html/2611.20688)).

The results come from AgenticVBench. Codex + VIVID on GPT-5.6-sol scores **58.6 ± 3.8** against 38.4 ± 6.3 native. Claude Code + VIVID on Claude Fable 5 scores 55.1 against 32.4 (+22.7). OpenCode on GPT-5.5 scores 37.1 against 27.4. Human experts score 88.5 ([VIVID Table 1](https://arxiv.org/html/2611.20688)). Token overhead is +11–53%, and a run costs $1.32–5.29 ([VIVID §5.2, Table 8](https://arxiv.org/html/2611.20688)). In the ablation, removing memory drops Repair from 43.0 to 22.9. Repair stays the weakest category, because better observation does not supply denoising or colour correction ([VIVID Table 2, §6.1](https://arxiv.org/html/2611.20688)). One caveat matters for UberLens: the memory ablation removes the task-state files and the evidence store together. Retrieve was called in only 10–32% of tasks, so much of memory's value probably comes from version pinning and task state rather than from retrieval. That is an inference the paper does not test.

### AgenticVBench: the editing benchmark, and its failure modes

AgenticVBench (Cao, Zheng, Song and Hu, Philo Labs) has 100 tasks built with 20 industry experts: 18 Assembly, 18 Repair, 28 Sequencing and 36 Repurpose. Programmatic verifiers score Assembly, Repair, Sequencing and the Format pillar of Repurpose. Expert binary rubrics score Repurpose's Visual, Narrative and Sound pillars: about 30 items per task, 1,069 in all ([arXiv:2605.27705 §2](https://arxiv.org/html/2605.27705)). The original paper graded those rubrics with humans. A companion VLM grader agrees with them 96–98% of the time. The VIVID paper scored Repurpose with Gemini 3.1 Pro and Claude Opus 4.7, so Repurpose comparisons across the two papers are approximate ([AgenticVBench App. C, F](https://arxiv.org/html/2605.27705); [VIVID B.4](https://arxiv.org/html/2611.20688)). The original best stack scored about 31% (GPT-5.5 + Codex). Changing only the harness moved GPT-5.5's Assembly score by 20 pp, and a full sweep with 3 runs per configuration cost about $7,477 ([§3, App. G](https://arxiv.org/html/2605.27705)).

The failure analysis bears directly on the index-first question. **83% of Repurpose failures were "long-context information loss"**: agents spent their budget on full-source Whisper or repeated thumbnailing and never assembled a cut. **65% of Repair failures were temporal**: the agent picked the wrong window, with a median start error of 15–100+ s ([Table 1](https://arxiv.org/html/2605.27705)). Yet editor scene notes added +23 pp on a hard Repurpose task, and agents ignored cinematic fields (removing camera_movement cost 1 pp, while removing the slot description cost 27) ([§3.4](https://arxiv.org/html/2605.27705)). Together these say that a good summary helps, but building one by brute force inside the task budget is how agents fail. The repo's license and dataset hosting could not be read **[unverified]**. Some sources cannot be redistributed and come only as retrieval instructions plus hashes.

### HKUDS VideoAgent: a tool router with a shallow shot pipeline

"VideoAgent: All-in-One Framework for Video Understanding and Editing" (Zhou, Huang, Wang, Zhou, Wu, Xia and Huang; arXiv:2606.23327, v2 3 Jul 2026) should not be confused with three earlier papers of the same name: 2403.10517, 2403.11481 and 2410.10076 ([arXiv](https://arxiv.org/abs/2606.23327)). Its shot pipeline runs once, with no checks. It captions fixed 10-second segments (3 frames each, Gemini-2.5-flash), map-reduces the captions into a summary, and has GPT-4o write a storyboard of **at most two sentences per scene**, with the scene count set to the number of detected "beats". Those beats are RMS-energy peaks, not real beat tracking. Each line is matched by ImageBind text→video cosine with no similarity threshold, never reusing a segment and skipping the first and last 10% of every source. A VLM then returns a single start-frame index at 1 fps for the target duration ([repo videorag, vid_editor.py, rhythm_story_gen.py](https://github.com/HKUDS/VideoAgent)). The paper says "ImageBind and CLIP", but CLIP is not in the code's retrieval path. The paper's experiments used MiniCPM-V 2.6 int4 and 3-second segments, so the released defaults differ from what was evaluated ([PDF A.4](https://arxiv.org/pdf/2606.23327)).

The orchestration layer has 33 registered agents with pydantic I/O schemas. Most are audio, TTS and singing tools. The face-swap and lip-sync agents listed in the paper (Viggle, Kling) are absent from the code. Claude-3.7 picks from 20 hand-written intents, which map to tool subsets, then designs a graph and has a second Claude call judge it. The judge's reasoning is fed back for up to 3 regenerations. Execution follows the LLM's linear chain, asks the user via `input()` for missing values, and has no repair ([multi.py, intents.yml, registry.json](https://github.com/HKUDS/VideoAgent)). Two results are useful. Removing graph optimization drops judged success from 0.95/0.93 to 0.70/0.69 on Claude-3.7. **Removing intent filtering leaves accuracy flat but raises cost 1.7–3.8×**, so intent filtering saves cost and does not improve accuracy ([Table 3](https://arxiv.org/pdf/2606.23327)). The LLM judge was validated on only 30 graphs, and it leans toward false positives ([§3.5](https://arxiv.org/pdf/2606.23327)). The human study (3.7 against 3.9 for hand-made edits, 26 raters drawn from the project's own community) is roughly 5% below human, not the "4%" claimed ([Table 6](https://arxiv.org/pdf/2606.23327)).

### EditDuet: a blind critic and the impossible-action problem

EditDuet (Sandoval-Castañeda, Russell, Sivic, Shakhnarovich and Caba Heilbron; SIGGRAPH 2025) assembles B-roll over a fixed A-roll ([arXiv:2509.10761](https://arxiv.org/abs/2509.10761)). The editor makes one structured call at a time from a closed set: `search_collection` (CLIP top-5), `add_to_timeline`, `remove_from_timeline`, `switch_clip_positions`, `move_clip` and `DONE`. **The critic reads only a text shot list** (captions, shot type, camera motion, durations) and answers with free-text `give_feedback` or `RENDER`. The authors skipped a VLM critic because of token cost. The editor never sees the user request, so in effect the critic plans for it ([PDF §3.3, Prompt #2](https://arxiv.org/pdf/2509.10761)). Early critics asked for things like "shoot a new video from a different angle", "add transitions" or "combine clips", and the editor responded by hallucinating functions such as `combine_clips`. Prompt constraints ("Videos can only be added, removed, and moved", "always includes one corrective action") were not enough. The fix was per-collection self-supervised exploration that mines 5 demonstrations for each agent, at about 82 minutes per collection ([§3.4, Supp. B, E](https://arxiv.org/pdf/2509.10761)). With Llama3.1-8B as both agents, adding a critic alone cut failures from 23.8% to 19.5%. Adding the mined demonstrations brought failures to 8.2% and coverage to 89.8% ([Table 1](https://arxiv.org/pdf/2509.10761)). So **the critic pays off only once its feedback is grounded in what the editor can do**. A GPT-4o pairwise judge on keyframe grids agreed with the human majority 80.6% of the time, against 78.7% agreement among humans ([§3.5.1](https://arxiv.org/pdf/2509.10761)).

### Auto-Director: a critic that watches, routes and freezes

Auto-Director (Chen, Zhu, Ji, Jiang, Zhong and Zhang; arXiv:2610.28346, accepted at MMM 2027) runs four agents on Gemini 3.1 Pro: planning (a fact-grounded script), material, editor and critic ([arXiv](https://arxiv.org/abs/2610.28346)). The material agent detects shots with PySceneDetect and **burns the shot ID and timestamp into keyframes** before an MLLM captions them. Removing this tagging drops Semantic Alignment from 4.23 to 3.54. The script is at most 10 scenes, each a triple (narration Tᵢ, visual query Qᵢ, duration window Dᵢ). **The critic samples keyframes from the rendered draft**, scores each scene 1–5 on semantics and on aesthetics, and sends exactly one typed signal to the stage that should fix it: `F_retrieval` (re-query) and `F_layout` (reframe) and `F_timing` (durations, transitions) go to the editor, and `F_script` (no footage exists) goes to the planner. Scenes scoring ≥4 on both are frozen, and the loop stops when all pass or after τ = 3 rounds ([PDF §3.2–3.4, §5.2, Table 2](https://arxiv.org/pdf/2610.28346)). It scores 4.19/5 on its own VEdit-Bench, against 3.46 for HKUDS VideoAgent and 4.62 for professional editors. Removing the critic costs 0.3–0.5 points on every dimension ([Tables 1–2](https://arxiv.org/pdf/2610.28346)). The judge is an unnamed MLLM (r = 0.73 against humans). The paper reports neither cost nor the critic's false-accept rate, and the critic prompt and the number of keyframes it samples per scene are not published.

### Related loops: code gates, per-segment re-execution and negotiation

**CutClaw** (arXiv:2603.29664) edits 1–3 hours of footage to music. Its Reviewer is a rejection gate that drops a candidate at once on a protagonist-presence, overlap, beat-grid-duration or quality failure. Removing the Reviewer moves scores by at most 1.6 points (Visual Quality 77.6 → 76.0), and AV Harmony is slightly *higher* without it ([arXiv](https://arxiv.org/abs/2603.29664)). **Crayotter** (arXiv:2606.07636) persists every plan, timeline state, tool call and intermediate render as an artifact, and on a failed check "re-executes the corresponding segment, rather than restarting the complete edit" ([arXiv](https://arxiv.org/abs/2606.07636)). **GLANCE** (arXiv:2604.05076) adds an Observe–Think–Act–Verify inner loop and negotiates conflicts between merged sub-timelines ([arXiv](https://arxiv.org/abs/2604.05076)). **DIRECT** (arXiv:2604.04875) has its Director validate the Editor's beam-searched (B = 3) sequences with bounded retries ([arXiv](https://arxiv.org/abs/2604.04875)). The 2024 HCI systems LAVE and ExpressEdit keep the human as the critic ([LAVE](https://arxiv.org/abs/2402.10294); [ExpressEdit](https://arxiv.org/abs/2403.17693)). Across all of them, critics help modestly and sometimes mixedly. The consistent 2026 pattern is local revision: freeze what passed and redo only the failing segment.

### MMLVE-Agent: generative entity edits checked shot by shot

"Thinking on Shots" (Wu, Long et al.; arXiv:2608.26809, MIT) edits pixels. It ADDs, DELETEs or MODIFYs entities with a commercial video-to-video model and leaves the cut structure unchanged ([arXiv HTML](https://arxiv.org/html/2608.26809); [LICENSE](https://raw.githubusercontent.com/Wucy0519/MMLVE/main/LICENSE)). Four pieces carry over to UberLens: shots as the unit of work; a **Global Memory Card**, a before→after reference image of the entity built from its top-6 keyframes across shots; a **≥2-of-3 VLM vote** on entity presence before a shot is edited at all; and **P-NEF** feedback, which returns both a "keep" prompt and an "avoid" prompt so that fixes do not break what was already right. The evidence is thin: 25 one-minute clips, a Gemini judge from the same family as the backbone, 45 human rankings, and a P-NEF ablation that is only qualitative ([paper Table 1, App. A](https://arxiv.org/html/2608.26809)).

### Index-first systems: describe everything, then re-check pixels anyway

The system that most clearly indexes first is **Ding et al.**, "Prompt-Driven Agentic Video Editing System" (arXiv:2509.16811). It runs Gemini 2.0 Flash over overlapping 15-minute segments with a scratchpad, then over 5-minute scenes extracting dialogue, affect and cinematography roughly every 20 s, then a reconciliation pass. The result is a synopsis, scene breakdowns and a character graph, reused for both QA and recap editing ([arXiv HTML v2](https://arxiv.org/html/2509.16811v2)). The reconciliation pass carries the weight: without it, detail scores fall from 4.46 to 2.39. Its AI recaps scored 2.75 against 4.38 for humans on "editing professionalism", and users complained of latency and of having no previews ([§4](https://arxiv.org/html/2509.16811v2)). CutClaw indexes shots into scenes and injects character names from Whisper. HIVE, CineAgents and WeVisCut also index, but they were read only at abstract level ([CutClaw](https://arxiv.org/html/2603.29664); [HIVE](https://arxiv.org/html/2507.02790v2); [CineAgents](https://arxiv.org/abs/2604.10456); [WeVisCut](https://arxiv.org/abs/2610.38352)). **Every index-first system looks at pixels again before it commits a cut, and none reports the cost of building the index or compares index-first against on-demand search at equal budget.**

## UberScene already supplies most of the edit harness

UberScene (github.com/prefix-tree/uberscene, MIT, read at commit 3d2979b) makes one TSX file the video. Cuts can name media moments instead of seconds (`word:12`, `word:23.end`, `shot:1`, `silence:3`, `marker:intro`), and those resolve from the transcripts and shots in the manifest "again after every edit, so a cut stays on its word when the clip is trimmed or moved" ([time.md](https://github.com/prefix-tree/uberscene/blob/main/docs/guide/time.md)). Set against the papers, its tooling lines up almost one-to-one with what VIVID, CutClaw and Auto-Director had to build.

| Paper mechanism | UberScene equivalent |
|---|---|
| VIVID `verify` (format, decode, review windows) | `uberscene lint` (exit 1 on error), `inspect` (errors on its first line, `--json`), `--check-layout` (exit 3, typed rules `frame-edge / safe-zone / captions / subject` with file:line and the smallest fix), plus `ffprobe`/`ffmpeg -xerror` on the export ([checking.md](https://github.com/prefix-tree/uberscene/blob/main/docs/guide/checking.md)) |
| VIVID `inspect` on the output, review windows around cuts | `uberscene look`: by default the first frame of each clip, both sides and the middle of every transition, and each title once; `--around <id>`, `--without <effect>`, `--motion`, `--listen` (level, words, LUFS, clipping); every cell labelled with time, frame and element ([cli.md](https://github.com/prefix-tree/uberscene/blob/main/docs/reference/cli.md)) |
| Auto-Director's burned-in shot ID and timestamp | The labels on `look` cells and the legend beside the image |
| VIVID source↔output time map | `inspect` prints each clip's source range and the words it plays |
| EditDuet's closed action set | **98 typed actions** (`clip/trim`, `clip/split`, `clip/slip`, `transition/add`, `caption/update`…) run through an `Executor`. `validate` returns typed errors (`ELEMENT_NOT_FOUND`, `OUT_OF_BOUNDS`…), `can()` dry-runs an action, `affordances(state, id)` lists the actions an element accepts, `invert` always gives the undo, and any action that introduces a new error is refused as `BREAKS_FILE` ([editing.md](https://github.com/prefix-tree/uberscene/blob/main/docs/guide/editing.md)) |
| Crayotter's persisted artifacts | The file is the edit: every round is a diff of `video.tsx`, and the patch log is replayable |
| Freezing passed segments, re-running one segment | The frame cache keys each frame on "everything that decides its pixels" (resolved props, media, settings, fonts, UberScene and Chrome versions), so after an edit only changed frames are redrawn ([cli.md, The frame cache](https://github.com/prefix-tree/uberscene/blob/main/docs/reference/cli.md)) |

This changes how VIVID's version-pinned evidence should map across. VIVID pins evidence to a hash of a rendered *file*, so every re-render makes all earlier output evidence stale. In UberScene a render is a function of the TSX text, the media, and the UberScene and Chrome versions (the export runs only on Chrome 157). Its identity can therefore be computed **before rendering** from those inputs, and evidence about rendered frames can be pinned to the **per-frame cache key**. A critic's "scene 3 is cluttered at 12.4 s" then stays valid after an edit to scene 5, and becomes stale exactly when a frame it looked at changes. That gives Auto-Director's freezing and Crayotter's per-segment re-execution as a property of the data, with no extra bookkeeping. Evidence about *source* footage should be pinned VIVID-style to the asset's content hash, and its time recorded both in seconds and as a transcript-word or shot reference, so it survives trims. Two caveats. UberScene's frame cache identifies media by size and modification time, not content, so UberLens must hash content itself or propose an upstream change. And no UberScene document found in this review promises byte-identical renders across machines **[unverified]**: the "deterministic render" premise should be tested by rendering twice and comparing frame hashes before anything relies on it.

## The edit loop these sources imply

The loop that best fits the evidence is VIVID's tools-plus-prompt harness wrapped in Auto-Director's critic discipline, with CutClaw's gates in front and UberScene as the editor's hands. It runs as follows.

**Perception tools.** The editor sees media through UberLens's existing perception tools, reshaped toward VIVID's `inspect`: window, overview and audio modes, a native-pixel ROI, at most 24 frames per call, contact sheets of 8, and bounded requests that return a version-pinned `next_request`. Inspection is layered, sparse overview first and dense windows second, and full-source transcription is not the first move. That ordering is VIVID's own case study (a 24-frame overview of a 5,640 s film, then local word-level transcription) and the remedy for AgenticVBench's top failure ([VIVID App. C](https://arxiv.org/html/2611.20688); [AgenticVBench Table 1](https://arxiv.org/html/2605.27705)).

**Edit tools.** The editor writes UberScene actions, never FFmpeg commands. Each is dry-run with `can()` and applied by the `Executor`, and the TSX diff is the record.

**Evidence memory.** Every observation is stored with an opaque evidence ID, the media version (asset content hash, or render-input hash plus frame key), the decoded timestamps and the crop. Evidence is never silently reattached to a newer version.

**Code checks before the critic.** `lint`, `inspect` errors, `--check-layout`, decode and format checks against the brief, duration windows, repeated clips and out-of-bounds trims all run as code. Only a render that passes them is shown to the critic, as CutClaw rejects a candidate on a hard violation before any perceptual judgment ([CutClaw](https://arxiv.org/abs/2603.29664)).

**Critic.** The critic watches: `look` sheets of each changed segment, the `--listen` strip, and that segment's intent (Auto-Director's narration, query and duration window). It returns per segment `{segment_id, scores: {semantic, aesthetic}, failure: retrieval | script | layout | timing | ok, keep: [...], fix: action}`. Every `fix` must be an action from that element's `affordances()` that passes `can()`, and anything else is rejected before it reaches the editor. This removes EditDuet's function-hallucination failures by construction, without 82 minutes of exploration.

**Stopping.** Segments that pass are frozen, and the critic re-examines only frames whose cache key changed. The loop allows at most 3 rounds at a ≥4/5 bar. When the budget runs out, the agent returns the best version with the failing segments flagged and the reasons stated.

**Division of labour.** System-1 runs the gates, chooses which segment to critique next and handles routine verdicts. System-2 is the perceptual critic and the planner.

**Index-first or on-demand.** The evidence argues for on-demand search with an amortised, lazily built index. Ding et al. and CutClaw show that an index gives the planner the whole-timeline view that restructuring needs. AgenticVBench shows agents failing when they try to build one inside the task budget. Every index-first system re-checks pixels anyway. UberScene's manifest already holds a free first layer (transcripts, shots, silences, subject boxes). A Ding-style narrative index should be built only when a project expects several edits or questions on the same footage. It should be cached by asset content hash and fed to ForeSeek's PREDICT step as **priors with `provenance = index`, never as evidence**, so that design.md's rule that memory reflects what was seen still holds. Whether the index pays for itself is unmeasured anywhere, and UberLens can measure it as frames and cost per query against the number of queries on the same footage.

### (a) Adopt from the papers

1. **§1 Sources table.** Add VIVID (arXiv:2611.20688, MIT): tools, version-pinned evidence, output review. Add Auto-Director (arXiv:2610.28346): typed, routed, freezing critic. Add EditDuet (arXiv:2509.10761): closed editor actions, and the negative result for blind free-text critics. Add CutClaw (arXiv:2603.29664): hard-constraint gates. Add MMLVE-Agent (arXiv:2608.26809): presence voting, keep/fix feedback. Add HKUDS VideoAgent (arXiv:2606.23327): intent-filtered tool subsets. Add Ding et al. (arXiv:2509.16811): narrative index. Record the corrections in the first table of this report.
2. **New §13 "Edit mode".** Add `mode: "edit"` to `AgentState`, with the loop: plan → edit (UberScene actions) → code gates → render/look → critic → route → revise, with freezing and a 3-round budget ([Auto-Director §3.4](https://arxiv.org/pdf/2610.28346); [VIVID §3](https://arxiv.org/html/2611.20688)).
3. **§2 versions.** Add `MediaVersion` with `asset_id = "asset_" + sha256(relpath + "\0" + sha256(content))[:24]`. Rewriting a file makes a new version, and old evidence stays recallable and stays attached to its own version ([memory.py](https://github.com/yuwenhan07/VIVID)).
4. **§2 evidence.** Add `Evidence {evidence_id, version, kind, timestamps_decoded, crop, coverage}` and give `MemoryEntry` a `version` and an `evidence_ids` field. Store evidence in SQLite plus content-addressed blobs, re-hashed on recall ([VIVID A.3](https://arxiv.org/html/2611.20688)).
5. **§3 perception tools.** Reshape `get_frames`/`get_clip`/`get_audio` toward VIVID `inspect` modes (window ≤600 s, overview, audio ≤120 s, `roi`, ≤24 frames, sheets of 8, bounded with `next_request`). Add `catalog`, `transcribe` (returns completed and pending ranges) and `retrieve` (evidence ID first, then text) ([harness_protocol.py](https://github.com/yuwenhan07/VIVID)).
6. **§3/§4 prompt rules.** Add VIVID's three guardrails (sampled frames ≠ continuous coverage; transcript ≠ listening; technical checks ≠ quality), "a miss does not establish absence", and layered inspection (overview, then dense windows; never full-source ASR first) ([VIVID A.1–A.4](https://arxiv.org/html/2611.20688); [AgenticVBench Table 1](https://arxiv.org/html/2605.27705)).
7. **§13 edit tools.** The editor's only write path is UberScene's `Executor` (`can` → `execute`, `invert` for undo). Checks are `lint`, `inspect --json`, `--check-layout --json`, `where`, `look`, and render with `--out`/`--draft`. Never generate FFmpeg commands ([editing.md](https://github.com/prefix-tree/uberscene/blob/main/docs/guide/editing.md)).
8. **§13 code gates before the critic.** Lint and inspect errors, layout issues, decode, duration/aspect/codec against the brief, repeated sources, out-of-bounds trims and duration windows are deterministic and block the critic ([VIVID verify](https://arxiv.org/html/2611.20688); [CutClaw](https://arxiv.org/abs/2603.29664)).
9. **§13 critic input.** The critic receives per-segment `look` sheets with the cells labelled (time, frame, element id), the `--listen` strip, and the segment intent (T, Q, D) ([Auto-Director §3.2–3.4](https://arxiv.org/pdf/2610.28346)).
10. **§13 critique schema and routing.** Per segment: scores (semantic, aesthetic 1–5) and one failure from `retrieval | script | layout | timing | ok`, routed to the editor (retrieval, layout, timing) or the planner (script) ([Auto-Director §3.4](https://arxiv.org/pdf/2610.28346)).
11. **§13 actionable feedback only.** Every failure carries exactly one corrective action, which must be in `affordances()` and pass `can()`. Reject the critique otherwise ([EditDuet Prompt #2, Supp. B](https://arxiv.org/pdf/2509.10761)).
12. **§13 freezing and limits.** Freeze segments at ≥4/5 on both scores. Allow at most 3 rounds. At budget, return the best version, flag the failing segments and give reasons ([Auto-Director §5.2](https://arxiv.org/pdf/2610.28346)).
13. **§13 review windows.** Plan output review from the timeline: each cut, transition, caption and title. This is `look`'s default sheet plus `--around` ([VIVID A.4](https://arxiv.org/html/2611.20688)).
14. **§2/§8 task state and continuation.** Persist the brief, the working plan and a bounded memory index outside the context, continue into a fresh context at a checkpoint, and carry the budget over ([VIVID A.1, A.5](https://arxiv.org/html/2611.20688)).
15. **§13 keep/fix feedback.** The critic returns what to keep alongside what to fix, and a revision must not regress kept items. This is weakly supported: P-NEF's ablation is qualitative only ([MMLVE](https://arxiv.org/html/2608.26809)).
16. **§13 presence before per-shot action.** Before acting on "every shot with X", take a ≥2-of-3 VLM presence vote per candidate shot, with candidates pruned by belief ([MMLVE](https://arxiv.org/html/2608.26809)).
17. **§3/§7 tool subsets by intent.** Offer the editor only the action families the brief needs. This is a cost lever with no accuracy effect ([VideoAgent Table 3](https://arxiv.org/pdf/2606.23327)).
18. **§8 budgets for edit mode.** Start from VIVID's 200 iterations and 1,800 s per task and ≤24 frames per inspect, and count critic calls ([VIVID Table 6](https://arxiv.org/html/2611.20688)).
19. **§9 evaluation for edit mode.** Report on AgenticVBench against the native agent on the same model. Ablate inspection, memory and output review VIVID's way. Score rendered outputs, never plan validity. Use a judge from a different model family from the critic, validated on a small human set, with a pairwise keyframe-grid judge as the cheap regression metric ([VIVID Table 2](https://arxiv.org/html/2611.20688); [EditDuet §3.5.1](https://arxiv.org/pdf/2509.10761); [VideoAgent §3.5](https://arxiv.org/pdf/2606.23327)).

### (b) Our extensions: label and ablate

20. **Render identity before rendering.** `render_version = hash(TSX text, media content hashes, props, UberScene version, Chrome version)`. Gate this on a determinism test (render twice, compare frame hashes) **[unverified premise]**.
21. **Per-frame evidence pinning.** Pin output evidence to UberScene's frame-cache key, so critic findings survive edits elsewhere and expire exactly when their frames change. Ablate against VIVID's whole-file invalidation.
22. **Content hashes for source media.** UberScene keys media by size and mtime. UberLens hashes content, and could propose this upstream.
23. **Evidence coordinates in media terms.** Store `word:N` / `shot:N` / `silence:N` alongside seconds for evidence about source footage, so it survives trims and moves.
24. **Critic only on changed frames.** Use the frame-cache diff to choose what the critic re-watches. Measure critic calls and quality against re-watching the whole cut.
25. **Critique as a dry-run patch.** The critic's fix is an action list checked with `can()` and applied as one `batch/apply`, with each round committed as a TSX diff and undone with `invert`.
26. **System-1 decision points for editing.** Add `gate_verdict`, `next_segment_to_critique`, `critic_verdict` and `route_failure`, escalating to System-2 under the existing rules. No editing paper uses a separate fast model.
27. **Watching vs reading critic.** Compare the same critic on `look` sheets against `inspect` text. EditDuet and Auto-Director sit at the two ends, and no paper compares them with the same critic.
28. **Lazy narrative index.** Build a narrative index from manifest transcripts, shots and silences plus Ding-style coarse, fine and reconcile passes, cached by asset content hash and built only when several edits or queries are expected. Ablate index-first against on-demand at equal budget as a function of query count.
29. **One store with provenance.** Index entries and observations share one store with `provenance: index | observed` and a confidence. Index entries feed PREDICT as priors and never confirm a belief interval.
30. **Visual anchor store.** Allow a small, typed, version-pinned reference-image store for entity consistency (the Global Memory Card equivalent) as the single exception to text-only memory.
31. **Embedding retrieval over evidence.** Add embedding retrieval over evidence text and keyframes on top of VIVID's literal search, and ablate it, since VIVID's retrieve is used in only 10–32% of tasks.
32. **Deterministic plan checks.** If edit plans become multi-step graphs, check acyclicity, port/type matching and intent coverage in code, and keep the LLM only for semantic fit. This replaces VideoAgent's LLM-only validation.

## Conclusion

The editing papers all reach for the same remedy, an agent that can see its own output and remember what it saw. Most of their engineering goes into making that possible on top of FFmpeg, which has no notion of what an edit means. UberScene removes that layer. Its edits are typed, validated and invertible, its renders are labelled and cached per frame, and its checks report like a compiler. UberLens's contribution on the edit side is therefore not another harness. It is the discipline the papers found: evidence pinned to versions, code gates before taste, a critic that watches and can only ask for what the editor can do, and freezing. On top of that comes one new capability that only video-as-code allows, evidence pinned to single frames, so a critique expires exactly when the pixels it judged change.

The open questions are empirical, and the sources leave them open. No paper measures a critic's false-accept rate, compares a watching critic with a reading one, or tests whether a precomputed index beats on-demand search at equal cost. These are the experiments UberLens should run first, because each one decides how much of the loop above is worth its calls.
